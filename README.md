# Wildberries Search Trends Service
Тестовое задание на стажировку в RWB.

## Быстрый старт

### Требования к окружению
Для полноценного запуска, тестирования и работы с проектом на вашей тачке должны быть установлены:
* **Go 1.26**
* **Docker** и **Docker Compose**

Для проверки работоспособности, тестирования и использования всех возможностей `Makefile`, необходимо установить эти Go-утилиты:
```bash
# Утилита для E2E нагрузочного тестирования (make load-test)
go install github.com/bojand/ghz/cmd/ghz@latest

# Утилита для тестирования gRPC API из консоли
go install github.com/fullstorydev/grpcurl/cmd/grpcurl@latest

# Официальный линтер (make lint)
go install github.com/golangci/golangci-lint/cmd/golangci-lint@latest
```

### Запуск проекта
Проект полностью упакован в Docker. Управление через `Makefile`:
- `make run`        - подъем докера, запуск проекта
- `make test`       - прогон тестов
- `make bench`      - запуск бенчмарков ядра
- `make load-test`  - запуск нагрузочного тестирования gRPC
- `make stop`       - остановка и очистка

После `make run` сервис будет доступен на порту 50051

### Примеры gRPC запросов:

#### TrendService

##### Получить Топ-N трендов:

```bash
grpcurl -plaintext \
  -import-path ./api/trend/v1 -proto trend.proto \
  -d '{"limit": 10}' \
  localhost:50051 trendservice.TrendService/GetTopN
```

#### StopListService

##### Добавить слово в стоп-лист:

```bash
grpcurl -plaintext \
  -import-path ./api/stoplist -import-path . -proto api/stoplist/stoplist.proto \
  -d '{"word": "казино"}' \
  localhost:50051 stoplistservice.StopListService/AddWord
```

##### Удалить слово из стоп-листа:

```bash
grpcurl -plaintext \
  -import-path ./api/stoplist -import-path . -proto api/stoplist/stoplist.proto \
  -d '{"word": "казино"}' \
  localhost:50051 stoplistservice.StopListService/DeleteWord
```

##### Получить все слова из стоп-листа:

```bash
grpcurl -plaintext \
  -import-path ./api/stoplist -import-path . -proto api/stoplist/stoplist.proto \
  -d '{}' \
  localhost:50051 stoplistservice.StopListService/GetAllWords
```

## Контракт данных (Kafka)
JSON-контракт для входящих сообщений в топике `trend-search-events`:
```JSON
{
  "session_id": "uuid-v4-or-device-id",
  "timestamp": 1716550000000,
  "normalized_query": "iphone 15 pro"
}
```

### Обоснование полей:
- `session_id` - поле для защиты от парсеров/накруток. С его помощью реализована дедупликация запросов, т.е. 1 уникальная сессия = 1 засчитанный уникальный запрос в минуту
- `timestamp` - время генерации события на клиенте (в миллисекундах). Позволяет отбрасывать устаревшие события, даже если консьюмер по какой-то причине отстал от брокера
- `normalized_query` - поисковый запрос (ожидается, что поисковый сервис уже очистил его от спецсимволов, привел к нижнему регистру и т.д.)

## Обоснование архитектуры

### 1. In-Memory ядро

По ТЗ у нас не будет данных старше 5 минут, а также будет частая работа с чтением/записью, поэтому SQL решения категорически не подходят. Поэтому я склонялся в сторону кэша. От Redis отказался из-за того, что сетевые походы создавали бы слишком высокую и неоправданную нагрузку, а ещё для Redis было бы тяжело реализовать эффективный алгоритм шардирования.
Поэтому я решил хранение реализовать прямо в памяти.

### 2. Шардирование и кольцевой буфер

Если бы все хранилось в одной мапе, то при высокой нагрузке участились бы коллизии, мьютексы блокировали бы работу сервиса намертво и в целом оперативной памяти плохо было бы.
Поэтому для хранения статистики за последние 5 минут я реализовал кольцевой буфер на 6 бакетов (по 1 на каждую минуту). В каждом бакете, чтобы горутины консьюмера не блокировали друг друга при записи, каждый минутный бакет разбит на 256 независимых шардов, каждый из шардов защищен своим `sync.RWMutex`.
Такое решение на бенчмарках показывает нулевые аллокации памяти при вставках.

### 3. Materialized View
Согласно ТЗ, запросов на чтение в 10-50 раз больше, чем на запись. Вычисление топа (мерж 256 мап и сортировка кучи) при каждом пользовательском запросе при высоком RPS создаст слишком высокую нагрузку на CPU. Поэтому запущен фоновый воркер, который раз в 2 секунды пересчитывает Топ-100 и кладет его в кэш. Метод `GetTopN` просто копирует готовый слайс за O(1).

### 4. Стоп-лист

Для стоп-листа ипользуется Redis. Для минимизации сетевых задержек я решил использовать библиотеку `rueidis`, т.к. в ней под капотом реализовано кэширование на стороне клиента. Но т.к. мы при добавлении запросов чаще будем **не попадать** в ключи, а `rueidis` не кэширует `Nil` ответы, то для стоп-листа также сделан in-memory кэш.

### 5. Брокер сообщений

В данной задаче нам нужно просто считывать входящие запросы, поэтому нам нужен тупой и быстрый брокер. По этой причине я не рассматривал RabbiqMQ. Из оставшихся вариантов: Kafka и NATS - я выбрал Kafka, поскольку это более знакомая для меня технология и с NATS я ещё не сталкивался.

## Компромисы и бизнес-логика

### Про In-Memory ядро

Из минусов такого подхода можно отметить, что при запуске/перезапуске/ сервиса он первые 5 минут работы не будет иметь данных об актуальных значениях. Но как по мне этот минус полностью перекрывается скоростью работы и простотой разработки, а также второстепенностью самого сервиса.

### Про кольцевой буфер

Работа с записью в шарды и очистка бакетов реализована через скользящее окно, привязанное ко времени. Т.к. бакетов всего 6, то в ходе работы мы копим данные не ровно за 5 минут, а за отрезок времени, который постепенно возрастает от 5 до 6 минут, а потом при очистке резко сбрасывается к 5 минутам опять.
Если требуется приблизить эти оконные значения к 5-ти минутам, то можно увеличить количество бакетов, из минусов - станет больше мап от шардинга.

### Про фоновый расчет Топ-100

Когда юзер делает запрос, то он получает не самые свежие данные, а данные, которым в худшем случае 2 всего секунды. Т.е. выдача результатов сервиса будет всегда отставать на 2 секунды от реального положения, но этот минус целиком перекрывается тем, что чтение занимает O(1).

### Про остановку сервиса

В программе везде передается контекст и добавлена обработка сигнала ОС `SIGINT` и `SIGTERM`. При их чтении запускается процесс graceful shutdown

### Про деградацию стоп-листа

Я использовал паттерн Fail-Open. Если Redis со стоп-листом падает или не отвечает, сервис залогирует ошибку, но пропустит слово в тренды. Из минусов - есть риск пропустить в рекомендации матерные слова и пр. слова из стоп-листа, но в условиях высокой нагрузке мне кажется это маловероятным, т.к. большинство пользователей будут просто искать то, что им нужно.

### Про валидацию стоп-слов

Программа сейчас сделана таким образом, что в стоп-лист можно записать только слова. Попытка записать предложение/выражение не пройдет. Связано это с тем, что для проверки у нас поисковый запрос разбивается на отдельные токены, следовательно хранить в стоп-листе строки с пробелами не имеет смысла.

## Результаты нагрузочного тестирования

Вы можете самостоятельно провести E2E обстрел сервиса, для этого нужно установить [ghz](https://github.com/bojand/ghz) и запустить команду:
```bash
make load-test
```

Скрипт автоматически сгенерирует 1,000,000 событий в Kafka, дождется их обработки ядром и запустит gRPC-обстрел.
